# 直結優先を維持した最短距離配送（2026-09-22）

## 採用した変更

Source／Relayに共通で、同色Sinkへの直結を最優先する。直結がない場合のランダム選択を、同色Sinkまでの合計実経路長が最小となるRelay選択へ変更した。途中のRelayの直結優先も残り距離に反映する。

- 直結がすべて満杯なら待機する。間接経路の方が短くても迂回しない。
- Relay候補では最初のLineを含む実経路長を合計する。最短が満杯なら等距離の空き候補だけを代替にでき、ステップ数・接続作成順で決定する。
- 同色Sinkへの到達経路がなければBufferで待つ。異色Sinkや循環だけの経路へ送らない。
- 複数直結の作成順は既存仕様を維持する。残り距離は空きを考えない通常時の先頭直結を使う。
- 色ごとの逆向きDijkstra経路表を再利用する。接続・予約・取消・経路切替・Node追加で失効し、In-FlightのFLOWは現在のLineを進める。
- `RouteWaitingFlows()` から乱数引数を除去した。生成色の乱数は維持する。

- 最終EditMode: **158/158成功**。既存の輸送・予約・Pause・Wave・FLOW保存を含む。
- 最終PlayMode: **53/53成功**。ゲージ・混雑の線種・ホバー・配線操作・シーン連携を含む。
- コンパイルError/Warning **0**、最終テスト後Console Error/Warning **0**。

従来の「出口のないRelayへランダム配送して満杯を作る」テスト準備を変更した。共有の `RelayCongestion` は補助Sourceから実際に出発させ、到着前にSinkへの出口を削除することで混雑を作る。Domainの内部状態の直接変更やFLOWの消去は使っていない。補助Sourceを使う表示テストはSimulationDriverを止め、明示的なDomain操作で表示を更新する。

最初のPlayMode実行は51/53。表示テストで後から追加した補助Sourceを既存FlowSimulationが知らない問題を、表示テストの更新入口をDomain操作へ揃えて修正した。Node 360のホバー確認は同じ実行で失敗し、その後の関連7件と最終全体53件は成功した。
